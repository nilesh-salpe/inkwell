Converting JSON to CSV

JSON is a tree and CSV is a grid, so the conversion always involves a decision. Here is what to decide, and the spreadsheet traps waiting at the other end.

The only shape that converts cleanly

A flat array of objects maps onto a table with no ambiguity — keys become the header, each object becomes a row:

[
  { "id": 1, "name": "Ada",   "role": "Engineer" },
  { "id": 2, "name": "Grace", "role": "Architect" }
]

Anything else requires you to choose how to lose information.

Nested objects

A row cannot contain a row, so nested objects get flattened, conventionally with dotted keys:

{ "user": { "name": "Ada", "team": { "id": 7 } } }
→  user.name,user.team.id
       Ada,7

This is fine two levels deep and unreadable at five. If the nesting is deep, the honest answer is that the data is not tabular and a CSV will mislead whoever opens it.

Arrays inside a row

Three defensible options, and the right one depends on the reader:

  • Join — read,write in one cell. Human-readable, but you have just put your delimiter inside a field, so the quoting had better be right.
  • Explode — one row per array element, other columns repeated. Correct for analysis; changes the row count, which surprises people.
  • Re-encode — put the raw JSON in the cell. Lossless and ugly.

Objects that do not share keys

Real data is rarely uniform. Take the union of every key across every object, and leave a cell empty where an object lacks it. The alternative — using the first object's keys as the header — silently drops fields, which is how data goes missing without anyone noticing.

Quoting, properly

RFC 4180 is short and worth knowing. A field must be quoted if it contains the delimiter, a double quote, or a line break. A literal quote inside a quoted field is written twice:

id,name,note
1,"Hamilton, Margaret","She said ""ship it"""
2,Ada,"line one
line two"

Both of those rows are valid and both break naive splitting on commas. If you are writing a parser, handle quotes before you handle delimiters.

Then someone opens it in Excel

Most CSV pain happens after the conversion:

  • UTF-8 needs a BOM. Without one at the start of the file, Excel on Windows mangles accented characters and anything non-Latin.
  • Leading zeros vanish. 007 becomes 7, so postcodes and product codes get quietly corrupted.
  • Long numbers lose precision. Anything past 15 digits — a tweet id, a bigint primary key — is rounded. Treat those as text.
  • Dates are reinterpreted according to locale, so 03/04 changes meaning depending on who opens it. ISO 8601 is the only safe format.
  • The delimiter is regional. Locales that use a comma as the decimal separator expect semicolon-delimited CSV.
  • Formula injection is a real vulnerability. A field starting with =, +, - or @ is executed as a formula when the file is opened. If the data came from users, prefix such fields with an apostrophe.

A checklist

  1. Is the JSON a flat array of objects? If not, decide consciously what to flatten or drop.
  2. Build the header from the union of all keys, not the first row.
  3. Quote per RFC 4180 and escape embedded quotes by doubling.
  4. Write ISO dates, and keep ids and codes as text.
  5. Add a BOM if a spreadsheet is the destination.
  6. Open the result and read the last row — truncation hides at the bottom.

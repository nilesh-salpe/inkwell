Converting Markdown to PDF

Three approaches, what each one gets wrong, and how to control page breaks, code blocks and fonts so the result looks deliberate rather than dumped.

Why this is harder than it looks

Markdown has no concept of a page. It describes a document as a stream of blocks, and every block is as tall as its content. A PDF is the opposite: a fixed grid of pages that content must be poured into. Everything awkward about the conversion comes from that mismatch — a heading stranded alone at the bottom of a page, a code block sliced in half, a table that runs off the right margin.

So the real question is not "which converter" but "which converter lets me control pagination".

Option 1 — Print from a browser

Render the Markdown to HTML, then use the browser's own print pipeline with a print stylesheet. This is what the editor on this site does.

Good: text stays selectable and searchable, fonts stay sharp at any zoom, links remain clickable, and the file is small because nothing is rasterised. You also get the full CSS paged-media model, which is the only reason fine control is possible at all.

Watch out: you must enable Background graphics in the print dialog or shaded code blocks and callouts come out white. Headers and footers are the browser's, not yours, unless you turn them off.

Option 2 — Pandoc with a LaTeX engine

pandoc notes.md -o notes.pdf --pdf-engine=xelatex \
  -V geometry:margin=25mm -V mainfont="Iowan Old Style"

Good: genuinely typeset output — real hyphenation, ligatures, proper widow and orphan control, cross-references, bibliographies. If the document is long or academic, nothing else comes close.

Watch out: a full TeX distribution is several gigabytes, error messages are famously cryptic, and styling means learning a template language. Overkill for a two-page README.

Option 3 — An editor extension

VS Code extensions and similar tools usually wrap a headless browser, so the output matches option 1. Convenient inside an existing workflow; less controllable, because the print stylesheet is someone else's.

Controlling the output

Force a page break

There is no Markdown syntax for this, so converters invent one. Here, a line containing only \pagebreak starts a new page. In CSS terms every approach ends up at the same property:

.pagebreak { break-after: page; }

Stop headings being stranded

A heading at the very bottom of a page, with its text overleaf, is the most common flaw in generated PDFs. One line fixes it:

h1, h2, h3, h4 { break-after: avoid; }
p, li { orphans: 3; widows: 3; }

Keep code blocks whole

Long code samples split across pages are hard to read. Ask for them to stay together, and to wrap rather than run off the edge — a PDF has no horizontal scrollbar:

pre, table, blockquote, figure { break-inside: avoid; }
pre { white-space: pre-wrap; word-wrap: break-word; }

Show link targets

A hyperlink is useless on paper unless the reader can see where it goes:

a[href^="http"]::after { content: " (" attr(href) ")"; font-size: 8pt; }

Choose print fonts deliberately

Screen and paper want different things. A serif face at 11pt reads better in print than the sans-serif you use on screen; keep sans for headings so the hierarchy stays obvious.

A practical recipe

  1. Write in Markdown, previewing as you go.
  2. Insert \pagebreak where a section genuinely must start fresh.
  3. Export to PDF and choose Save as PDF as the destination.
  4. Turn on Background graphics, turn off headers and footers.
  5. Skim for stranded headings and split tables. Adjust and repeat.

For a README, a proposal, meeting notes or a one-pager, that is the whole job. Reach for pandoc when you need a table of contents that numbers itself, footnote-heavy academic text, or a hundred pages.
